# Storage Agent 43 — design

Status: in progress on `claude/charming-faraday-4ig7zx`. When 43 ships, this
page becomes history and CLAUDE.md is the contract.

## Thesis

Up to 42 the product was a question-and-answer tool: the user asks, the agent
reads from nothing, answers, and forgets everything but ad-hoc notes. 43 makes
it agent native:

- **Parity.** What the user can do in the window, the agent can do with a tool
  (or propose, where the user must approve).
- **Primitives, not features.** The app adds a few general capabilities —
  a workspace, time, a voice to the user, self-knowledge, approved action —
  and every "feature" (a daily public-access watch, a cost dashboard, an
  estate map, a remediation) is the agent composing them from a prompt.
- **One shared, durable workspace** the agent organises and the user can
  open, instead of five silos.
- **Reachable.** Other agents can use it over MCP.

The test for every change: does it let a real user, on a real account, with a
real model, get a correct answer or a correct change, with no feature code
written for that request?

## Tools after 43

| Tool | Status | Purpose |
|---|---|---|
| `call` | kept | one read operation of a bundled service |
| `query` | kept | read-only script over many calls, files and SQL |
| `probe` | kept | one unsigned request to a public host or the account endpoint |
| `more` | kept | any stretch of a kept result, body, attachment or workspace file |
| `delegate` | kept | an independent investigation by a child agent |
| `ask` | kept | a question for the user |
| `workspace` | **new** | the agent's durable files and SQL across tasks |
| `self` | **new** | what the agent is and may do; proposals for settings |
| `schedule` | **new** | future turns, durable, with an unattended budget |
| `notify` | **new** | tell the user something now |
| `change` | **new** | propose one write; the user approves; the app runs it |
| `memory`, `tool`, `skill`, `render`, `discover` | **removed** | folded into `workspace`, `query` and `self` |

Each tool's description is its contract; the prompt does not list tools.

## `workspace`

A folder, `<data>/workspace/`, opened from the window (Settings → Workspace,
and a sidebar entry), plus one agent-owned SQLite file `workspace/db.sqlite`.

- Actions: `list {path?}`, `read {path, offset?, length?}`, `write {path,
  content}`, `append {path, content}`, `move {from, to}`, `delete {path}`,
  `search {text, path?}`, `sql {sql, params?}` (read and write, this file
  only; no `ATTACH`, no `load_extension`).
- Conventions the agent may follow or not (they are in the prompt as one
  line): `skills/` (Markdown with `name`/`description` front matter),
  `notes/`, `data/` (datasets as SQLite), `scripts/` (JavaScript a `query`
  can run by path), `board/` (views the window pins), `exports/` (files for
  the user).
- Paths are relative, normalised, and never leave the folder (no `..`, no
  absolute paths, no symlinks followed out).
- Secrets are redacted on write, like every other store.
- **Board.** Every `board/*.view.json` that holds a valid view document is
  shown on the Board, newest first. The agent updates a pinned view by
  writing the file again. No pin tool: the folder is the board.
- **Exports.** A file under `exports/` gets a link in the conversation; the
  user saves it with the system dialog.
- **Skills.** Bundled skills ship read-only (`skills` in the app bundle).
  The prompt lists bundled skills by name and description; skills in the
  workspace are listed too, but inside an untrusted-data block marked with
  their file, because the agent or anything it read may have written them.
  A workspace skill never silently replaces a bundled one: both are listed.
- `query` sees the workspace: `read()`, `sql()` over `data/*.sqlite` and
  `db.sqlite`, and `run({path, args})` for a script.

## `self`

Read: the model it runs on (provider, id, context window, thinking), what
this task has spent, the accounts (name, id, endpoint, region, auth kind,
scope, whether changes are allowed — never a key), its schedules, the app
version, the workspace path, today's date, the services and read operations
it can call.

Write, applied at once (low risk, parity): `title` (rename this task),
`pin` (pin or unpin this task).

Propose, applied only when the user approves in the window: `scope` (an
account's bucket list), `allow_changes` (turn changes on or off for an
account). The proposal is shown like a change.

## `schedule`

- `create {name, prompt, at? | every?, budget_tokens?}`: `at` is an ISO time;
  `every` is `"<n>m" | "<n>h" | "daily HH:MM" | "weekly <day> HH:MM"` in the
  user's local time. `list`, `cancel {name}`.
- Each run is a turn in the schedule's own task (created on first run, named
  after the schedule), so its history is a normal conversation the user can
  open, steer or stop.
- A run is a pi durable task that sleeps until it is due (`sleepUntil`),
  submits the turn, waits for it, and sleeps again. No second queue: pi owns
  timing and survives restarts. A run missed while the app was closed runs
  once at launch.
- **Unattended budget.** A scheduled run stops when it has used its token
  budget: the schedule's own, else Settings' default (100,000 tokens). This
  is the one harness limit, and it applies only when nobody is watching; a
  run the user opens and steers becomes attended and the budget lifts.
- The app runs in the tray and can start at login (Settings), so schedules
  run with the window closed.

## `notify`

`notify {title, body, task?}`: a system notification and an entry in the
window's inbox. Clicking it opens the task. Settings' notification switch and
quiet hours apply; the agent cannot override them. Rate: a scheduled run may
notify at most once unless the user replies (stops alert storms).

## `change`

The agent may propose a write. It never holds a write-capable client.

1. **Opt-in per account.** Settings → account → *Allow changes* (off by
   default), optionally with separate write credentials (a profile or keys);
   without them the read credentials are used.
2. **Allowlist.** Reversible bucket configuration only:
   `s3:PutPublicAccessBlock`, `s3:DeletePublicAccessBlock`,
   `s3:PutBucketPolicy`, `s3:DeleteBucketPolicy`,
   `s3:PutBucketOwnershipControls`, `s3:PutBucketEncryption`,
   `s3:PutBucketVersioning`, `s3:PutBucketLifecycleConfiguration`,
   `s3:DeleteBucketLifecycle`, `s3:PutBucketCors`, `s3:DeleteBucketCors`,
   `s3:PutBucketLogging`, `s3:PutBucketTagging`, `s3:PutBucketAcl`,
   `s3control:PutPublicAccessBlock`. Never object writes, never deletes of
   data, never IAM in 43.
3. **Proposal.** `change {provider_id, service, operation, input, reason}`
   is checked (allowlist, operation input members, scope), then the app reads
   the current state with the matching read (`GetBucketPolicy` for
   `PutBucketPolicy`, …) and stores it as the **snapshot**. The tool returns a
   `change` view — the exact call, before and after — and ends the turn.
4. **Approval is out of band.** The window shows **Approve** and **Reject**.
   Approve goes over IPC to the main process, which runs exactly the stored
   call with the write client — the model never sees an approval token and
   cannot approve. The result (or error) is written to the task, and a turn
   is submitted: "The user approved change <id>; it returned … Verify it."
5. **Verify and roll back.** The agent re-reads to verify. Every applied
   change has **Roll back**, which proposes the inverse from the snapshot
   (put the old document back, or delete what did not exist) and needs the
   same approval.
6. A scheduled (unattended) run may propose but nothing runs until a person
   approves it.

## Safety foundations (before any of the above)

1. `checkCall` validates every input member against the operation's modelled
   input and refuses unknown members, so a scope check can never pass on a
   member the SDK would drop.
2. `s3control:GetDataAccess` joins `NEVER`.
3. A saved model key is sent only to the provider and base URL it was saved
   for.
4. Redaction runs on the whole result before it is cut into pieces.
5. Compaction is set from the model's window (`reserveTokens`,
   `keepRecentTokens`, `backgroundTokens` per model through
   `compaction.modelOverrides`), output is capped to a share of the window,
   and a model whose window cannot hold the fixed prompt plus a working
   margin is refused with the reason (minimum 16k).

## Data

From 43 the host schema migrates forward; it is never cleared. 42's stores
move into the workspace once: memory documents to `notes/memory/<key>.json`,
agent methods to `scripts/<name>.js` (+ `.schema.json`), user skills to
`skills/`, kept datasets to `data/`. `memory.sqlite` and `agent_tools` are
then retired.

## MCP

`storage-agent --mcp` (the Electron binary in headless mode, so the vault
works) serves `call`, `query`, `probe`, `more` and `workspace` (read) over
stdio, with the same scope, redaction, envelope and audit. `change`,
`schedule` and `notify` are window-only in 43. Consuming other MCP servers is
44.

## Acceptance (real-model evals, no feature code)

1. "Every morning at 9, tell me if any bucket became public."
2. "Make a storage-cost board per bucket and refresh it weekly."
3. "From now on treat vendor account 999988887777 as a trusted partner."
4. "Put this investigation in a CSV for me."
5. "Only look at the logs bucket in this account." (a scope proposal)
6. "Block public access on web-assets." (a change proposal, approved,
   verified, rolled back)

Each runs against the fake world with a large model and a ~16k-window model.
