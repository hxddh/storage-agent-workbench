# Storage Agent v4.0.0

**The resident Agent for the storage estate. The estate is the object; Agent Tasks are how work is done. Migration 032. Storage stays read-only; one Agent and one submit path are unchanged.**

## Summary

Through v3.1 every Task started from nothing, and what it found ended with it. v4.0 keeps what the Agent learns about the user's storage and looks after it:

- **Estate.** Completed surveys and config reviews leave a durable record per account: the buckets, their posture (status flags only) and when each was last checked. Every new task starts knowing it.
- **Issues with a lifecycle.** Deterministic observations become Issues, fingerprinted per provider + bucket + rule: open → fix proposed → resolved → recurred when they come back. The user can accept a risk.
- **Fix and Verify.** A fix is text the user applies with their own credentials; Storage Agent never writes to storage. Verify is a read-only re-check.
- **Proactive watch.** Opt-in per account and off by default. The Sidecar sweeps the account read-only on its own clock and opens **one** task only when something new turns up, with one notification.
- **Home: what to care about now.** A readiness check when a model or storage account is missing; starters that need storage say so; *Your storage* and *Needs care*.
- **Trust.** A live golden task drives a real Execution against a real S3 server in CI.

## Why a major version

The product invariant changes. From v0.94 to v3.1 it was *the Agent Task is the application*. In v4.0 the Task remains the one place work happens, but the object the product keeps and the home starts from is the estate. CLAUDE.md, the canonical docs and the documentation contract change together.

## What changed

- **Migration 032** (`storage_estate_issues_watch`) adds four tables:
  - `estate_buckets`
  - `issues` and `issue_events` (append-only lifecycle)
  - `watch_schedules`
- **Ingestion** (`sidecar/app/estate/store.py`):
  - After an `account_discovery` or `bucket_config_review` run completes, `run_service.run_sync` projects its persisted, sanitized output onto the estate. Failures never break the run.
  - A survey that saw the whole account (not truncated, no include/exclude pattern) forgets buckets no longer listed and resolves their Issues.
- **Rules** (`estate/rules.py`). Seven rules:
  - public exposure (high)
  - wildcard principal
  - CORS open to all origins
  - no default encryption
  - incomplete public access block
  - no multipart cleanup
  - noncurrent versions never expire

  How the rules are applied:
  - Posture decides only what it can see.
  - A review with a blind spot (access denied, unreadable, unsupported) decides nothing.
  - Silence never resolves an Issue.
  - Model prose never opens or closes one.
- **Fix.** Generated fixes are deterministic templates: a CLI command, the JSON document and notes. Available fixes are PutPublicAccessBlock, PutBucketEncryption (SSE-S3) and lifecycle rules (abort multipart after 7 days; expire noncurrent after 30). Where the right fix depends on intent there is none, and the user asks the Agent in the task.
- **Verify** (`estate/verify.py`). Re-runs the rule's read-only review (`review_bucket_security` / `review_bucket_lifecycle`) after the provider scope check. Each run is recorded as a tool call and reports `still_present`, `resolved` or `inconclusive`.
- **Watch** (`estate/watch.py`).
  - Opt-in per provider, off by default, interval 1 h–7 d.
  - The tick runs on the Sidecar's clock: `STORAGE_AGENT_WATCH_TICK_SECONDS`, default 60 s.
  - A sweep runs the survey engine (≤ 500 buckets) and a read-only re-check of what posture cannot decide (≤ 25 buckets).
  - Only when a high or medium Issue was opened or came back does it open one Agent Task through `runtime.submit`, with the evidence in its Direction.
  - With no model configured, no task is opened and the Issues stay on the home.
  - Turning the watch off stops a scheduled sweep between phases.
  - The last 3 sweep runs per provider are kept.
- **Prompt.** Every task receives a bounded `known_estate` block after `configured_providers`: providers with known bucket counts and last check, and ≤ 12 open Issues. No posture documents are included.
- **API.**
  - `GET /estate`
  - `GET /issues`, `GET /issues/{id}`
  - `POST /issues/{id}/fix`, `POST /issues/{id}/verify`, `POST /issues/{id}/accept`
  - `GET` / `PUT /estate/watch/{provider_id}`, `POST /estate/watch/{provider_id}/run`
- **Frontend.**
  - `api/estate.ts`.
  - `components/EstateHome.tsx`: readiness, *Your storage* and *Needs care*. Each Issue expands to its detail, the fix with Copy, Verify, Open task (the task that found it) and Accept risk.
  - Starters that need storage say so when none is configured.
  - `settings/ProviderWatch.tsx`: Off · 6 h · Daily · Weekly, Check now, and the last result, shown in each cloud provider row.
  - `hooks/useWatchAlerts.ts`: one OS notification per sweep that found something, and the task list refreshes.
  - The start page scrolls from its top once the estate makes it taller than the window.

## Preserved

- Read-only storage. There is no mutating S3 tool, and fixes are text for the user.
- Secrets only in the encrypted vault; server-side provider scope; sanitized and bounded context; no chain-of-thought.
- One Agent and one submit path: the watch opens its task through `runtime.submit` like any Direction. Nothing on the home submits work.
- Result-first Task, the side pane, the Composer and every v3.x surface.

## Contracts

- **Sidecar:** `sidecar/tests/test_v400_estate.py` pins:
  - the rules, blind reads and fix text;
  - the lifecycle (opened → fix proposed → resolved → recurred) and accept;
  - most-severe-first ordering and Chinese titles;
  - the `known_estate` prompt block and hiding a deleted provider;
  - the golden task: a real Execution with the fake model against a real S3 server (moto) — survey → review → Issues → the user applies the fix → Verify resolves → the problem returns → recurred.
- **Sidecar:** `test_v400_watch.py` pins:
  - off by default;
  - a due sweep opening one task through the runtime;
  - nothing new costing no model call;
  - turning the watch off stopping a sweep between phases;
  - no model meaning no task;
  - interval bounds;
  - one sweep at a time;
  - run retention.
- **Frontend:** `components/v400.test.tsx` pins:
  - readiness, including never claiming a missing prerequisite while offline;
  - starters that need storage;
  - the estate list, Open task, Generate fix and Verify;
  - no submit path on the home;
  - the watch row;
  - one notification per sweep.
- The documentation contract moves to v4.0.0.

## Known gaps

- Signed and notarized installers still need the maintainers' certificates.
- The live golden task runs against moto, a real S3-protocol server that does not verify signatures. A MinIO service job is a candidate.
- The watch covers configuration posture. Cost anomalies need routine inventory evidence and are not watched yet.
- Readiness reports what is configured. It does not run the provider probes; the inline Test in Settings does.
